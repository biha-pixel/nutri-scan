# Architecture — NutriScan

This document explains the system architecture of the NutriScan application in plain language.
It is meant to be read by a beginner software engineering student.

---

## What Is Architecture?

**Architecture** is the high-level plan for how a software system is structured.
It answers:
- What pieces exist?
- What does each piece do?
- How do the pieces communicate?
- What are the rules each piece must follow?

Think of it like the floor plan of a building. The floor plan doesn't tell you what colour the
walls are or what furniture is inside. It tells you where the rooms are, how they connect, and
what each room's job is.

---

## The Two Deployable Units

A **deployable unit** is a piece of software that runs independently — it is shipped and hosted
separately from the others.

NutriScan has two:

```
┌─────────────────────────────────┐     ┌─────────────────────────────────────────────┐
│   Mobile App                    │     │   Backend Server                             │
│   (Expo / React Native)         │────▶│   (Next.js — deployed to Vercel or similar)  │
│   runs on the user's phone      │     │   runs in the cloud                          │
└─────────────────────────────────┘     └─────────────────────────────────────────────┘
```

Why two units and not one? The mobile app runs on the user's device, which means anyone can
inspect or reverse-engineer it. The backend runs in a server we control, which means secrets
(API keys) and sensitive logic live there safely.

## The Full Data Flow

Here is what happens from the moment the user taps "Scan Food" to the moment nutrition
information appears on screen:

```
User taps "Scan Food"
        │
        ▼
[ 1. Mobile App ]
  - User takes photo or picks from gallery
  - App compresses the image
  - App sends image to backend via HTTPS (POST /api/scan)
        │
        │  HTTPS request  (multipart/form-data: image file)
        ▼
[ 2. Next.js API Route Handler — /api/scan ]
  - Validates the request (Zod): is the image present? is it an image type? is it within size limit?
  - Calls the AI Vision Service
        │
        ▼
[ 3. AI Vision Service ]
  - Sends image to Gemini multimodal API
  - Receives structured JSON: list of food items with names, confidence scores, portions
  - Validates the Gemini response (Zod)
  - Returns a FoodRecognitionResult to the API route
        │
        ▼
[ 4. Nutrition Lookup Service ]
  - For each identified food item, searches USDA FoodData Central
  - Selects the best match (or returns "no match" / "ambiguous match")
  - Normalizes USDA data into our internal NutritionInfo schema
  - Returns a list of NutritionResult objects
        │
        ▼
[ 5. Highlight Rules Engine ]
  - Evaluates each food item against rule-based thresholds
  - Example rule: protein > 20g per 100g → "Good source of protein"
  - These rules are NOT generated by AI — they are written by us
  - Returns a list of highlights per food item
        │
        ▼
[ 6. API Route Handler — assembles response ]
  - Combines: food identifications + nutrition data + highlights
  - Validates the outgoing response shape (Zod)
  - Sends structured JSON response back to the mobile app
        │
        │  HTTPS response  (JSON: food items, nutrition, highlights, serving size notes)
        ▼
[ 7. Mobile App ]
  - Receives and parses the JSON response
  - Displays nutrition facts for each identified food item
  - Shows highlights (e.g. "High in Vitamin C")
  - Shows confidence level for each food item
  - Shows serving-size assumption clearly
```

## The Modular Monolith

NutriScan's backend is a **modular monolith**.

**Monolith** means it is one application — one Next.js project, one deployment, one process.

**Modular** means that even though it is one deployment, its internal code is divided into
clearly separated modules with defined responsibilities:

```
backend/
├── app/api/          ← HTTP layer: receives requests, sends responses
├── lib/vision/       ← AI module: talks to Gemini (or a future replacement)
├── lib/nutrition/    ← Nutrition module: talks to USDA (or a future replacement)
├── lib/highlights/   ← Highlight module: rule-based benefit evaluation
└── lib/validation/   ← Zod schemas: defines what data shapes are valid
```

Each module has **one job**. The AI module identifies food — it does not look up calories.
The nutrition module looks up calories — it does not talk to the AI.

**Why not microservices?**
Microservices would mean deploying the AI module, the nutrition module, and the highlight module
as separate applications that communicate over a network. For a project at this stage, that adds
enormous operational complexity (separate deployments, network errors between services,
distributed tracing) without any real benefit. We will stay monolith until there is a concrete
reason to split.

## Provider Abstractions

Two external services can change in the future:
- The AI vision provider (currently Gemini, could become OpenAI Vision, Claude Vision, etc.)
- The nutrition data provider (currently USDA, may add Open Food Facts for packaged products)

We protect against that change using **provider abstractions** — a design where the rest of
the code talks to an interface, not directly to the provider's SDK.

```typescript
// The interface — what any vision provider must be able to do
interface VisionProvider {
  identifyFood(image: Buffer, mimeType: string): Promise<FoodRecognitionResult>
}

// The implementation — Gemini does it this way
class GeminiVisionProvider implements VisionProvider {
  async identifyFood(image, mimeType) { ... }
}

// The rest of the code only knows about VisionProvider, not GeminiVisionProvider
// Swapping Gemini for another provider = swap one class, touch nothing else
```

This pattern is called **Dependency Inversion** — the high-level module (the API route) depends
on the abstract interface, not on the concrete implementation (Gemini).

## What Lives Where (and Why)

| Location | What lives there | Why |
|---|---|---|
| Mobile app | UI screens, navigation, camera access, API calls to our backend | Runs on device, must be public |
| Backend `/api` | Route handlers, request/response validation | HTTP boundary — entry point |
| Backend `lib/vision` | Gemini integration, VisionProvider interface | AI logic isolated here |
| Backend `lib/nutrition` | USDA integration, NutritionProvider interface, normalization | Nutrition logic isolated here |
| Backend `lib/highlights` | Rule-based highlight evaluation | Business rules isolated here |
| Backend `lib/validation` | Zod schemas | All data contracts in one place |
| Environment variables (server only) | Gemini API key, USDA API key, Supabase service role key | **Never in the mobile app** |

## Future: Supabase

When we add user accounts and scan history, we will add Supabase:

```
[ Mobile App ] ──▶ [ Next.js Backend ] ──▶ [ Supabase (PostgreSQL + Auth) ]
```

Supabase provides:
- **PostgreSQL** — a relational database for storing scan history, user profiles
- **Auth** — managed authentication (sign up, sign in, JWT tokens)
- **Row Level Security (RLS)** — database-level rules that ensure users can only read their own data

We will add this when there is a concrete feature that requires it (e.g. "save scan history").

## Key Vocabulary

| Term | Plain-English Definition |
|---|---|
| **Deployable unit** | A piece of software that is deployed and runs independently |
| **Monolith** | One application, one deployment |
| **Modular monolith** | One deployment, but internally divided into clear modules |
| **Module** | A self-contained piece of code with one responsibility |
| **API** | A way for two software systems to communicate — you call it, it responds |
| **API Route Handler** | A function in Next.js that responds to HTTP requests |
| **HTTPS** | HTTP with encryption — how the mobile app talks to the backend securely |
| **JSON** | A text format for structured data — what APIs usually send and receive |
| **Zod** | A TypeScript library for validating that data matches an expected shape at runtime |
| **Provider abstraction** | A code pattern where you depend on an interface, not a specific implementation |
| **Interface** | A contract: "anything that implements this interface must have these functions" |
| **Environment variable** | A value set on the server that is not in the code — used for secrets |
| **RLS** | Row Level Security — a database-level rule controlling who can read/write each row |
